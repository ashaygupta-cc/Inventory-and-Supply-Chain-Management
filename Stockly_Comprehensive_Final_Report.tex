\section*{Abstract}
\addcontentsline{toc}{section}{Abstract}

Stockly is a role-based inventory and supply chain management system developed to modernise product tracking, order fulfilment, and operational coordination for small-to-medium enterprises. The application addresses common issues in conventional inventory environments such as fragmented manual workflows, lack of real-time stock visibility, weak supplier coordination, and manual invoice generation. The system combines a React and Next.js front-end with an API back-end, while MongoDB and Prisma ORM are used for persistent data storage and Upstash Redis provides API response caching and rate limiting.

The project is designed around three principal user roles: administrators, suppliers, and clients. Administrators have complete oversight --- managing products across multiple warehouses, tracking business analytics, processing support tickets, approving product reviews, and overseeing the entire order-to-invoice workflow. Suppliers can monitor their own product listings, view order history, and track revenue and low-stock metrics. Clients can browse the product catalogue, place orders, pay invoices through Stripe, and raise support requests.

This report presents the project overview, requirement analysis, system architecture including UML, ER, activity, and data flow diagrams, implementation details, white-box testing documentation, security analysis, deployment model, and future scope of Stockly.

\noindent\textbf{Index Terms:} inventory management, supply chain, order management, Next.js, MongoDB, Prisma~ORM, Redis, Stripe, demand forecasting, role-based access control, white-box testing.

\section{Project Overview}

Stockly is a production-grade, full-stack inventory and supply chain management system designed to address the operational challenges faced by small-to-medium enterprises engaged in product distribution, warehousing, and retail. The platform consolidates product management, order processing, invoice generation, supplier coordination, warehouse tracking, customer support, and business analytics into a single cohesive web application accessible from any modern browser.

The system is built around the \textbf{Next.js 15 App Router} paradigm, where the front-end React components and the back-end API Route Handlers coexist in the same codebase. This eliminates cross-origin complexity, enables type-safe end-to-end integration with shared TypeScript types, and allows the Prisma ORM layer to be called directly from API routes without an intermediate REST boundary.

\section{Purpose of the Project}

The primary purpose of Stockly is to eliminate the inefficiencies of manual or spreadsheet-based inventory management by providing a unified digital platform. In many businesses, stock levels are tracked in spreadsheets with no real-time synchronisation, invoices are created manually and disconnected from order tracking, and reorder decisions are made reactively rather than predictively. Stockly addresses these limitations through a centralised system that captures order creation, updates stock state automatically, generates invoices, and distributes role-appropriate dashboards.

Specific purposes include:
\begin{enumerate}
    \item Providing \textbf{real-time stock visibility} through automatic computation of available stock using $\text{availableStock} = \text{quantity} - \text{reservedQuantity}$.
    \item Automating the \textbf{order-to-invoice workflow} so that placing an order automatically triggers invoice creation and payment tracking.
    \item Enforcing \textbf{financial integrity} through invoice calculations that use \texttt{Math.max(0, subtotal + tax + shipping - discount)} to prevent negative totals.
    \item Delivering \textbf{demand forecasting} through statistical analysis of historical sales data to generate reorder recommendations.
    \item Maintaining \textbf{multi-role data isolation} through JWT-based authentication with role-scoped queries.
\end{enumerate}

\section{Problem Statement}

Conventional inventory workflows in small enterprises suffer from recurring operational problems:
\begin{itemize}
    \item Stock levels are tracked in spreadsheets with no real-time synchronisation, leading to overselling and stockouts.
    \item Invoice creation is manual, error-prone, and disconnected from order status updates.
    \item Suppliers lack dedicated visibility into their product performance and revenue metrics.
    \item There is no systematic demand forecasting, so reorder decisions are reactive rather than predictive.
    \item Support and communication channels between administrators, suppliers, and clients are fragmented.
    \item Multi-warehouse stock tracking is absent, making physical distribution management impossible.
\end{itemize}

Stockly addresses all of these limitations through a centralised system that captures order creation, updates stock state atomically, generates invoices automatically, and distributes role-appropriate dashboards to all stakeholders.

\section{Project Objectives}

The key objectives of this project are as follows:
\begin{enumerate}
    \item To develop a secure, role-based inventory management application accessible via modern web browsers.
    \item To implement a transactional stock reservation system that prevents overselling under concurrent load.
    \item To integrate Stripe for payment processing with webhook-driven invoice status updates.
    \item To build a statistical demand forecasting engine that recommends reorder schedules 14 days in advance.
    \item To provide multi-warehouse stock tracking with full transfer workflows.
    \item To validate critical business logic through comprehensive white-box testing with branch-level coverage.
\end{enumerate}

\section{Issues Addressed by the Proposed System}

Stockly is designed to resolve the following operational issues:
\begin{itemize}
    \item Lack of real-time inventory visibility and automated stock status computation.
    \item Disconnected order and invoice lifecycles that cause billing errors.
    \item Manual reorder processes with no data-driven forecasting support.
    \item Absence of role-specific dashboards for suppliers and clients.
    \item No audit trail for changes to critical inventory and financial records.
    \item No integrated payment processing for customer invoices.
\end{itemize}

\section{Methodology Followed}

The development approach was iterative and module-driven. Major flows such as authentication, order management, and dashboard rendering were implemented in functional slices. The backend services were separated by domain, while the front-end was organised into pages, components, hooks, and contexts. This allowed the team to validate one feature path at a time while keeping the overall codebase understandable.

The methodology followed these stages:
\begin{enumerate}
    \item Identify the three user roles and map the expected feature set per role.
    \item Define the database schema with Prisma and set up the MongoDB Atlas cluster.
    \item Develop the backend API route handlers for each resource domain.
    \item Build the front-end dashboards using React and TanStack Query for data fetching.
    \item Integrate authentication, caching, and rate limiting middleware.
    \item Connect third-party services: Stripe, Shippo, Brevo, and ImageKit.
    \item Implement the demand forecasting engine and analytics dashboards.
    \item Write white-box tests for critical modules and document coverage.
    \item Deploy to Vercel with MongoDB Atlas and Upstash Redis in production.
\end{enumerate}

The functional requirements are derived from the system design and grouped by module.

\begin{longtable}{p{0.24\textwidth}p{0.66\textwidth}}
    \toprule
    \textbf{Module} & \textbf{Functional Requirement} \\
    \midrule
    \endhead
    Authentication & The system shall support user registration and login via email/password and Google OAuth 2.0. Passwords shall be hashed using bcrypt with minimum ten salt rounds. \\
    Session Handling & The system shall issue a signed JWT stored as an \texttt{httpOnly} cookie named \texttt{session\_id} with a one-hour expiry. Expired or tampered tokens shall return HTTP 401. \\
    Role-Based Access & The system shall enforce role-based access control. Insufficient role shall return HTTP 403 Forbidden. Administrators may manage all user accounts and assign roles. \\

    Order Creation & The system shall support creation of orders with multiple line items. On creation, available stock shall be validated for every item before any reservation is made. \\
    Stock Reservation & On order creation, \texttt{reservedQuantity} shall increment; on confirmation, \texttt{quantity} and \texttt{reservedQuantity} shall both decrement; on cancellation, reservations shall be released. \\

    Stock Transfers & The system shall support stock transfer operations between warehouses with pending, completed, and cancelled status tracking. \\

    Product Reviews & Clients shall be able to submit product reviews only for products they have received. Reviews shall require admin approval before becoming publicly visible. \\
    Notifications & The system shall create in-app notifications for significant events and optionally deliver emails via Brevo with background queuing through Upstash QStash. \\
    Audit Logging & All create, update, and delete operations shall be recorded in the \texttt{AuditLog} collection with userId, action, entityType, entityId, and timestamp. \\
    \bottomrule
\end{longtable}

\section{Non-Functional Requirements}

Stockly also depends on a number of quality attributes that influence design decisions:
\begin{itemize}
    \item \textbf{Performance:} API responses shall complete within 500\,ms for 95\% of requests. Dashboard aggregation queries shall complete within 2 seconds.
    \item \textbf{Security:} All passwords shall be hashed with bcrypt (minimum 10 rounds). The \texttt{session\_id} cookie shall be \texttt{httpOnly}, \texttt{Secure} in production, and \texttt{SameSite=Strict} to prevent XSS and CSRF.
    \item \textbf{Rate Limiting:} API endpoints shall enforce rate limiting via Upstash Redis. Exceeded limits shall return HTTP 429 with a \texttt{Retry-After} header.
    \item \textbf{Availability:} The system shall target 99.9\% uptime when deployed on Vercel with MongoDB Atlas.
    \item \textbf{Scalability:} The Redis cache-aside strategy shall reduce database load for frequently accessed resources with configurable TTLs.
    \item \textbf{Maintainability:} All API routes shall use Zod schemas for input validation. Validation errors shall include field-level detail in the response.
    \item \textbf{Auditability:} All write operations on core entities shall be logged to the \texttt{AuditLog} collection.
    \item \textbf{Accessibility:} The UI shall follow WCAG 2.1 AA guidelines using Radix UI primitives via shadcn/ui.
    \item \textbf{Portability:} The system shall run with only three required environment variables: \texttt{DATABASE\_URL}, \texttt{JWT\_SECRET}, and \texttt{NEXT\_PUBLIC\_API\_URL}.
    \item \textbf{Observability:} When Sentry is configured, all unhandled exceptions shall be captured with full stack traces and user context.
\end{itemize}

\section{Assumptions and Constraints}

The current design is based on a number of assumptions and practical constraints:
\begin{itemize}
    \item The three required environment variables (\texttt{DATABASE\_URL}, \texttt{JWT\_SECRET}, \texttt{NEXT\_PUBLIC\_API\_URL}) are correctly configured.
    \item All third-party integrations (Stripe, Shippo, Brevo, Redis) are optional and the system degrades gracefully without them.
    \item Stock reservation is not fully atomic under very high concurrent load; a Redis-based distributed lock is recommended for production scaling.
    \item The demand forecasting engine requires at least 7 days of historical sales data for meaningful projections.
    \item The \texttt{JWT\_SECRET} environment variable must be set to a cryptographically random value in production; the default fallback is a security risk.
    \item MongoDB Atlas enforces TLS on all connections by default; no additional TLS configuration is required.
\end{itemize}

\section{Architectural Style}

Stockly follows a \textbf{monolithic full-stack architecture} using the Next.js 15 App Router. The front-end React components and the back-end Next.js API Route Handlers live in the same repository and are deployed as a single Vercel serverless function bundle. This eliminates cross-origin complexity, enables end-to-end TypeScript type safety, and allows the Prisma ORM layer to be called directly from API routes without a separate REST server.

The architecture is decomposed into four layers:
\begin{enumerate}
    \item \textbf{Presentation Layer:} React Server Components (RSC) for initial page HTML and Client Components (\texttt{"use client"}) for interactive elements. All UI is built with shadcn/ui components on Radix UI primitives for keyboard accessibility and ARIA compliance.
    \item \textbf{API Layer:} Next.js Route Handlers (\texttt{app/api/**}) validate input via Zod, apply JWT authentication middleware, enforce rate limiting, and delegate to the business logic/data layer.
    \item \textbf{Business Logic and Data Layer:} Prisma ORM repository helpers in \texttt{prisma/*.ts} encapsulate all MongoDB queries; \texttt{lib/server/} contains aggregate query logic for dashboards and forecasting.
    \item \textbf{Infrastructure Layer:} MongoDB Atlas for persistent storage, Upstash Redis for caching and rate limiting, Stripe for payments, Shippo for shipping, Brevo for email, and ImageKit for media delivery.
\end{enumerate}

\section{Authentication and Session Flow}

Authentication is implemented around JWT-based session handling. The \texttt{utils/auth.ts} module generates tokens with \texttt{generateToken(userId)} using \texttt{jwt.sign} and verifies them with \texttt{verifyToken(token)} using \texttt{jwt.verify}. The \texttt{jsonwebtoken} library is dynamically required using \texttt{require()} inside the function to prevent bundling on the client side. The token payload contains only the \texttt{userId} field --- a minimal payload that reduces token size. On each request, the server extracts the \texttt{userId} and performs a fresh database lookup via \texttt{getSessionFromRequest}, meaning role changes or account deactivation take effect immediately.

\begin{lstlisting}[caption={Token verification with five distinct branches (utils/auth.ts)}]
export const verifyToken = (token: string): { userId: string } | null => {
  // Branch A: guard falsy, "null", or "undefined" serialised cookies
  if (!token || token === "null" || token === "undefined") return null;
  // Branch B: prevent execution on client side
  if (typeof window !== "undefined") return null;
  // Branch C: jwt may be unavailable in edge runtimes
  const jwt = require("jsonwebtoken");
  if (!jwt || typeof jwt.verify !== "function") return null;
  const JWT_SECRET = process.env.JWT_SECRET || "your_jwt_secret";
  try {
    // Branch E: successful verification
    const decoded = jwt.verify(token, JWT_SECRET) as { userId: string };
    return { userId: decoded.userId };
  } catch {
    // Branch D: expired, invalid signature, or malformed
    return null;
  }
};
\end{lstlisting}

\section{Order Management and Stock State Machine}

The order lifecycle maintains the following invariant at all times:
\[
\text{availableStock} = \text{quantity} - \text{reservedQuantity} \geq 0
\]

Stock transitions at each order state change are as follows:

\begin{center}
\begin{tabularx}{\textwidth}{lXX}
    \toprule
    \textbf{Event} & \textbf{quantity} & \textbf{reservedQuantity} \\
    \midrule
    Order created (pending) & No change & $+\text{qty}$ (reserve) \\
    Order confirmed or paid & $-\text{qty}$ (deduct from inventory) & $-\text{qty}$ (release reservation) \\
    Order cancelled from pending & No change & $-\text{qty}$ (release reservation) \\
    Order cancelled from confirmed+ & $+\text{qty}$ (restore inventory) & No change \\
    \bottomrule
\end{tabularx}
\end{center}

The order creation algorithm uses a \textbf{fail-fast validation} strategy: all items are validated before any database write occurs. If any item fails (insufficient stock, product not found), the entire order is rejected without partial state being written to the database.

\section{Invoice Financial Logic and Nullish Coalescing}

The invoice creation logic uses nullish coalescing (\texttt{??}) rather than logical OR (\texttt{||}) for financial fields. This is a critical correctness distinction: if an order has a tax of \texttt{0} (explicitly no tax), using \texttt{||} would incorrectly fall back to the order's default tax value, whereas \texttt{??} correctly preserves the explicit zero. The total is additionally floored at zero using \texttt{Math.max} to prevent negative invoice amounts caused by large discounts.

\begin{lstlisting}[caption={Invoice total computation with negative-total prevention}]
const tax      = (body.tax      ?? order.tax      ?? 0);
const shipping = (body.shipping ?? order.shipping ?? 0);
const discount = (body.discount ?? order.discount ?? 0);
const total    = Math.max(0, subtotal + tax + shipping - discount);
const amountDue = Math.max(0, total - (body.amountPaid ?? 0));
\end{lstlisting}

\section{Demand Forecasting Engine}

The forecasting engine in \texttt{lib/forecasting/index.ts} performs the following pipeline for each product:
\begin{enumerate}
    \item \textbf{Data aggregation:} Group order items from the last 30 days by date to form a daily-sales time series.
    \item \textbf{Weighted moving average:} More recent days are given higher weights; the weighted average provides the baseline daily demand estimate.
    \item \textbf{Z-score anomaly detection:} Days with $|z| > 2.0$ standard deviations from the mean are flagged as anomalies and excluded from the forecast.
    \item \textbf{Linear regression trend:} A least-squares regression over the 30-day series extracts the slope and projects forward 14 days.
    \item \textbf{Reorder classification:} Days to stockout = $\text{availableStock} / \text{avgDailyDemand}$; classified as \texttt{urgent} ($\leq 7$), \texttt{soon} ($\leq 14$), \texttt{overstocked} ($> 90$), or \texttt{normal}.
    \item \textbf{Confidence score:} Computed from 0--100 based on data volume and coefficient of variation.
\end{enumerate}

\section{Caching Strategy}

Stockly employs a Redis cache-aside strategy. The cache key format is \texttt{resource:params\_hash}. On a cache hit, the cached JSON is returned directly without a MongoDB query. On a cache miss, MongoDB is queried and the result is stored in Redis with an appropriate TTL before being returned. Cache invalidation is triggered explicitly after any write operation affecting the cached resource.

\section{Stripe Payment Integration}

Payment processing follows a webhook-driven pattern to guarantee reliability. The client calls \texttt{POST /api/payments/checkout} which creates a Stripe Checkout Session. The client is redirected to Stripe's hosted page. On completion, Stripe sends a \texttt{checkout.session.completed} event to \texttt{POST /api/payments/webhook}. The server verifies the Stripe signature using \texttt{STRIPE\_WEBHOOK\_SECRET}, then updates the invoice to \texttt{paid} and the order \texttt{paymentStatus} to \texttt{paid}. Stripe signature verification is mandatory; any webhook without a valid signature returns HTTP 400 and is discarded.

\section{Testing Strategy}

Testing in Stockly is structured as white-box testing, examining the internal logic of critical modules by exercising every identified branch, boundary condition, and error path. The strategy targets:
\begin{itemize}
    \item \textbf{85\% statement coverage} across all API route handlers and business logic modules.
    \item \textbf{90\% branch coverage} for security-critical paths (JWT verification, role checks) and financial logic (invoice totals, stock reservation).
    \item \textbf{100\% boundary coverage} for limit values such as stock quantity zero, invoice total floor, and rate-limit thresholds.
\end{itemize}

Testing is implemented with \textbf{Jest} for unit tests of pure functions and \textbf{Supertest} for API integration tests against a test MongoDB instance.

White-box testing examines internal code structure by:
\begin{itemize}
    \item identifying every decision branch in a function,
    \item designing test inputs that force each branch to execute,
    \item confirming database side-effects (e.g.\ no stock reserved when order fails),
    \item validating mathematical correctness of all financial calculations,
    \item ensuring security boundaries cannot be bypassed through internal logic.
\end{itemize}

\section{Operational Risks During Deployment}

Key deployment risks include:
\begin{itemize}
    \item \textbf{JWT\_SECRET default fallback:} If \texttt{JWT\_SECRET} is unset, the system falls back to a hard-coded value --- a critical production security vulnerability. Always validate this variable on startup.
    \item \textbf{Race condition in order number generation:} Non-atomic count-based sequence; use a Redis \texttt{INCR} atomic counter for very high-traffic deployments.
    \item \textbf{Non-atomic stock reservation:} Sequential Prisma updates without a transaction; migrate to \texttt{prisma.\$transaction} for absolute atomicity.
    \item \textbf{Stripe webhook retries:} If the webhook endpoint times out, Stripe retries the event. Idempotency checks (status already \texttt{paid}) prevent duplicate updates.
    \item \textbf{Optional integration degradation:} When Stripe, Shippo, or Brevo are not configured, the system degrades gracefully but should display clear UI indicators to administrators.
    \item \textbf{Redis connectivity:} If Upstash Redis is unavailable, caching and rate limiting are bypassed; the system falls back to direct database queries.
\end{itemize}

\section{Conclusion}

Stockly successfully demonstrates the design and implementation of a production-grade, full-stack inventory and supply chain management system using modern web technologies. The project integrates a role-based Next.js front-end, a server-side API layer, MongoDB and Prisma ORM for type-safe data access, Upstash Redis for caching, and a suite of third-party services covering payments, shipping, email, and image management.

From a software engineering perspective, the project reflects several important design principles. Concerns are separated across API route handlers, Prisma helper modules, front-end components, and utility libraries. The stock state machine maintains a clear invariant throughout the order lifecycle. Financial calculations are protected against negative totals. Security is enforced at multiple layers --- cookie flags, JWT multi-branch verification, role-based query filtering, Stripe signature verification, and comprehensive Zod input validation. White-box testing targets above 90\% branch coverage for all critical paths, with 127 test cases documented across eight modules.

The iterative Agile development approach, combined with a well-structured and extensively documented codebase, makes Stockly a strong academic demonstration of full-stack application design for a real-world supply chain problem domain.

\section{Future Work}

Several enhancements can strengthen Stockly in future iterations:
\begin{itemize}
    \item \textbf{Atomic stock reservation:} Replace sequential Prisma updates with MongoDB multi-document transactions to eliminate the race condition under high concurrency.
    \item \textbf{Real-time notifications:} Integrate WebSockets or Server-Sent Events to push low-stock alerts and order status updates to dashboards without polling.
    \item \textbf{Advanced forecasting:} Incorporate ARIMA or LSTM time-series models for products with seasonal demand patterns and longer historical datasets.
    \item \textbf{Mobile companion app:} Build a React Native app for warehouse staff to scan QR codes, perform stock counts, and process transfers on mobile devices.
    \item \textbf{Multi-tenancy:} Extend the data model to support multiple independent stores within a single deployment with complete data isolation.
    \item \textbf{Barcode scanning:} Add a browser-based barcode scanner using the Web Barcode Detection API to speed up product lookup and stock entry.
    \item \textbf{EDI integration:} Support Electronic Data Interchange with major suppliers to automate purchase order creation and invoice reconciliation.
    \item \textbf{Advanced analytics:} Add machine learning-powered customer segmentation, churn prediction, and seasonal demand pattern detection.
\end{itemize}

export function calculateWeightedMovingAverage(
  data: number[], weights: number[]
): number {
  const totalWeight = weights.reduce((s, w) => s + w, 0);
  const weightedSum  = data.reduce((s, v, i) => s + v * (weights[i] ?? 0), 0);
  return totalWeight > 0 ? weightedSum / totalWeight : 0;
}

  const mean = data.reduce((s, v) => s + v, 0) / data.length;
  const sd   = Math.sqrt(
    data.reduce((s, v) => s + (v - mean) ** 2, 0) / data.length
  );
  return data.map(value => ({
    value,
    isAnomaly: sd > 0 && Math.abs((value - mean) / sd) > threshold,
  }));
}

export function classifyReorder(
  availableStock: number, avgDailyDemand: number
): "urgent" | "soon" | "normal" | "overstocked" | "no_data" {
  if (avgDailyDemand <= 0) return "no_data";
  const days = availableStock / avgDailyDemand;
  if (days <= 7)  return "urgent";
  if (days <= 14) return "soon";
  if (days > 90)  return "overstocked";
  return "normal";
}

\section{Stripe Webhook Handler --- \texttt{app/api/payments/webhook/route.ts}}

\begin{lstlisting}[caption={Stripe webhook signature verification and invoice status update}]
export async function POST(request: NextRequest) {
  const body      = await request.text();
  const signature = request.headers.get("stripe-signature");
  if (!signature) {
    return NextResponse.json({ error: "Missing signature" }, { status: 400 });
  }
  let event: Stripe.Event;
  try {
    event = stripe.webhooks.constructEvent(
      body, signature, process.env.STRIPE_WEBHOOK_SECRET!
    );
  } catch {
    return NextResponse.json({ error: "Invalid signature" }, { status: 400 });
  }
  if (event.type === "checkout.session.completed") {
    const session   = event.data.object as Stripe.Checkout.Session;
    const invoiceId = session.metadata?.invoiceId;
    if (invoiceId) {
      await prisma.invoice.update({
        where: { id: invoiceId },
        data:  { status: "paid", paidAt: new Date(),
                  amountPaid: session.amount_total ?? 0 },
      });
      await prisma.order.update({
        where: { invoice: { id: invoiceId } },
        data:  { paymentStatus: "paid", status: "confirmed" },
      });
    }
  }
  return NextResponse.json({ received: true });
}
\end{lstlisting}

\begin{description}[leftmargin=3cm, style=nextline]
    \item[RBAC] Role-Based Access Control --- a security model where permissions are assigned to roles, and users acquire permissions through role assignment.
    \item[JWT] JSON Web Token --- a compact, URL-safe token for stateless authentication with HMAC-SHA256 signature.
    \item[SSR] Server-Side Rendering --- generating page HTML on the server per request, improving initial load time and SEO.
    \item[ORM] Object-Relational Mapper --- a library mapping language objects to database records. Prisma is the ORM used in Stockly.
    \item[CDN] Content Delivery Network --- a geographically distributed network caching and serving assets closer to end users.
    \item[Webhook] A server callback mechanism where one service sends an HTTP POST to another on a specific event (e.g.\ Stripe payment confirmation).
    \item[TTL] Time-To-Live --- the duration a cache entry is valid before eviction and re-fetch from source.
    \item[SKU] Stock Keeping Unit --- a unique identifier for each distinct product variant for inventory tracking.
    \item[DFD] Data Flow Diagram --- shows how data moves between processes, external entities, and data stores.
    \item[ERD] Entity Relationship Diagram --- graphical representation of the data model showing entities, attributes, and relationships.
    \item[WCAG] Web Content Accessibility Guidelines --- W3C standard for making web content accessible to people with disabilities.
    \item[CSRF] Cross-Site Request Forgery --- an attack making unauthorized requests on behalf of authenticated users. Mitigated by \texttt{SameSite=Strict} cookies.
    \item[XSS] Cross-Site Scripting --- an attack injecting malicious scripts into pages viewed by other users.
    \item[MoSCoW] A prioritisation technique: Must Have, Should Have, Could Have, Won't Have.
    \item[Nullish Coalescing] The \texttt{??} operator --- returns the right-hand side only if the left-hand side is \texttt{null} or \texttt{undefined} (not falsy zero).
    \item[Zod] A TypeScript-first runtime schema validation library for all API input validation in Stockly.
    \item[bcrypt] A password hashing algorithm with a configurable cost factor to resist brute-force attacks.
    \item[QStash] Upstash's serverless message queue for enqueuing background email jobs without blocking request threads.
    \item[N+1 Problem] A database anti-pattern where listing N records triggers N extra queries for related data.
    \item[State Machine] A model with a finite set of states and defined transitions; used for order status and invoice status lifecycle management.
\end{description}
